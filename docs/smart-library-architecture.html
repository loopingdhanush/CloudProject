Smart Library Monitoring

Three library rooms send simulated sensor data. An edge gateway on the laptop cleans it, decides each room's state and forwards only the result. The latest state of every room lives in a digital twin, and a dashboard shows the whole library. All of it runs as 10 Docker containers in the Compose project smart-library.

The containers

Container names follow one pattern: library-<part>. The six library-ditto-* containers together make up Eclipse Ditto.

  1. Twins are created first

    When Docker Compose starts, Ditto comes up first. library-twin-setup then creates one Thing per room with its fixed attributes, plus one Thing for gateway statistics.

  2. Sensors publish

    library-sensors publishes a reading for each room every second to library/R01/telemetry, library/R02/telemetry and library/R03/telemetry.

  3. The broker delivers

    library-mqtt-broker passes every reading to the gateway, which subscribes to the wildcard topic library/+/telemetry.

  4. The gateway decides at the edge

    library-edge-gateway turns 10 readings into one result and publishes only that: a summary to library/<room>/summary, or an alert to library/alerts. That is about 91% fewer messages.

  5. The twin is updated

    The same result is sent as a REST PATCH to /api/2/things/library:<room>. nginx checks the login, the Ditto gateway routes the request, Things updates the twin and MongoDB stores it.

  6. The dashboard reads the twins

    Every 3 seconds the gateway asks Ditto for all three twins and draws the colour-coded room cards. Staff open http://localhost:1880/ui.

  1. Clean

    Broken JSON, missing or text values, and impossible values (occupancy −5, 70 °C, humidity 140%) are dropped and counted.

  2. Convert

    R02's Fahrenheit becomes Celsius and its equipment codes 0/1/2 become OFF/ON/FAULT, so all rooms use the same format: {"room":"R01","occupancy":42,"temperature":24.1,"humidity":52,"equipment":"OK"}.

  3. Window and features

    Each room collects 10 valid readings. The gateway then calculates average and peak occupancy, occupancy as a % of capacity, average temperature and humidity, how many readings broke a rule, and how many devices are in FAULT.

  4. Trend

    If average occupancy has risen in each of the last 4 windows and is above 70% of capacity, SeatAvailability becomes LIMITED, so staff can open another room early. At 100% or more it becomes FULL.

  5. Classify and decide

    The rules below set the status. CRITICAL goes out immediately as an alert. NORMAL and WARNING go out as one small summary. Either way, the room twin is updated.

NORMAL

20–26 °C, 40–60% humidity, occupancy below 80% of capacity, all equipment working.

WARNING

Temperature or humidity outside the limits, or occupancy between 80% and 100% of capacity.

CRITICAL

Occupancy above capacity, any equipment in FAULT, or temperature and humidity both outside the limits. Raises an immediate alert.

Docker management (Q1)

  1. Run and check health

    docker compose up -d starts everything. docker compose ps shows each container as healthy, and docker logs library-edge-gateway prints every CRITICAL alert.

  2. Failure and recovery

    docker compose stop nodered takes the gateway down, and the dashboard becomes unavailable. docker compose start nodered brings it back healthy.

  3. Update v1 → v2

    Setting GATEWAY_VERSION=v2 and running docker compose up -d nodered replaces the container with the v2 image. Its alerts also suggest an action, for example “Call technician for: computers”.
